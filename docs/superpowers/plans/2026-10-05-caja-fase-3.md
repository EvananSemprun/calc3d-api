## Decisiones tomadas antes de este plan

### 1. El desplegable NO puede recalcular la clasificación

Es la decisión que ordena toda la fase. Hoy la clasificación de cada asiento
—`operativo`, `deLaContraparte`, `isFilament`, y el reparto de un retiro entre
devolución de deuda (`applied`) y retiro puro— vive **adentro** de
`businessCash` (`packages/shared/src/calc/cash.ts`), como filtros anónimos
dentro de nueve llamadas a `suma()`.

Si el endpoint del desplegable rearma esos filtros por su cuenta, hay **dos
clasificaciones** que tienen que coincidir para siempre. El día que una cambie,
la pantalla va a mostrar un detalle que suma distinto que la línea de arriba.
Una pantalla de dinero que se contradice a sí misma es peor que no tener
desplegable: el dueño deja de creerle a las dos cifras.

**Se invierte `businessCash`: primero clasifica, después suma.** Una función
nueva `cashEntries(ledger, until?)` devuelve cada asiento con su categoría, y
`businessCash` pasa a ser un `reduce` sobre esa lista. El endpoint devuelve los
mismos asientos. Un solo lugar decide, y un test fija el invariante.

Es refactor del motor de dinero, que es lo más delicado del repo. El riesgo
está acotado por dos barreras que este plan impone:
- **Ningún test existente de `cash.spec.ts` se puede tocar.** Si uno se pone
  rojo, el refactor está mal, no el test.
- Un test nuevo exige `suma(entries de la categoría X) === businessCash[X]`
  para **las nueve** categorías.

### 2. Los asientos llevan `id`, no etiquetas

`cashEntries` devuelve `{ category, date, amount, id? }` y **nada de texto**.
`shared` es el motor puro: meterle `description`, `concept` o `note` lo ataría
a los nombres de columna de Prisma. La API hace el join `id → etiqueta` al
serializar.

Consecuencia: `CashLedger` gana un `id?: string` opcional en cada asiento. Es
aditivo —el motor lo ignora— así que ningún test existente que arme un ledger a
mano se rompe.

### 3. Un retiro produce DOS asientos

`businessCash` ya parte cada `WITHDRAWAL` en `debtRepayments`
(`min(amount, applied)`) y `ownerDraws` (`max(0, amount − applied)`). En
`cashEntries` eso son dos asientos con **el mismo `id`** y distinta categoría.
No es un efecto colateral del refactor: es exactamente lo que el dueño necesita
ver, porque es la distinción que pidió en el mensaje original —devolver una
deuda no es lo mismo que sacar plata— y hasta ahora solo existía como dos
números agregados.

### 4. `source` también va en `Sale` y `Payment`

El spec (§7 paso 7) las nombra y la fase 1 no las tocó. Sin eso, el desplegable
de "Ventas cobradas" mostraría 112 filas importadas **sin** la insignia mientras
el de "Gastos generales" las muestra con insignia: el dueño concluiría que esas
ventas las cargó él. Es un `ADD COLUMN ... DEFAULT 'MANUAL'`, aditivo y sin
backfill en la migración.

### 5. El backfill de "Importado" no toca producción en esta fase

El código de la insignia entra ya y **no muestra nada** hasta que el backfill
corra. El backfill va como script aparte, dry-run por defecto, con reversa.

La fecha de corte quedó resuelta contra la copia local del 01/10:

### 6. Lo que se suma al alcance del spec (autorizado por el dueño)

### 7. Lo que NO entra

- **Filtrar el desplegable por mes.** La Caja es acumulada desde el principio;
  un filtro de fecha es otra feature.
- **`accountId` por movimiento** y transferencias entre cuentas: sigue siendo
  fase 4.

- [ ] 1.3 — Escribir `cashEntries(ledger, until?)` moviendo los filtros tal cual
  están hoy. Un `WITHDRAWAL` emite hasta dos asientos, **omitiendo los de monto
  cero** (un retiro totalmente aplicado no debe aparecer como un `ownerDraws` de
  $0 en el desplegable):

```ts
/**
 * Cada asiento de la caja con su categoría. `businessCash` suma esto, y el
 * desplegable de la pantalla muestra esto mismo.
 *
 * ⚠️ ES LA ÚNICA clasificación. Si alguna vez hay una segunda —en la API, en el
 * front, en el reporte de Excel— el detalle y el total van a divergir el día
 * que una de las dos cambie, y la pantalla se contradice a sí misma.
 */
export function cashEntries(ledger: CashLedger, until?: Fecha): CashEntry[] {
  const hasta = until?.slice(0, 10);
  const vale = (d: Fecha) => !hasta || d.slice(0, 10) <= hasta;
  const out: CashEntry[] = [];
  const push = (category: CashCategory, x: { date: Fecha; amount: number; id?: string }) => {
    if (x.amount !== 0) out.push({ category, date: x.date, amount: x.amount, id: x.id });
  };

  const operativo = (e: CashLedger['expenses'][number]) => !e.isInvestment && e.paidBy !== 'LOAN';
  const deLaContraparte = (e: CashLedger['expenses'][number]) => operativo(e) && e.paidBy === 'OWNER';

  for (const v of ledger.sales) if (vale(v.date)) push('collected', v);
  for (const p of ledger.orderPayments) if (vale(p.date)) push('collected', p);

  for (const e of ledger.expenses) {
    if (!vale(e.date)) continue;
    if (operativo(e) && !e.isFilament) push('expenses', e);
    if (operativo(e) && e.isFilament) push('filament', e);
    if (e.isInvestment && e.paidBy === 'BUSINESS') push('equipment', e);
    if (deLaContraparte(e)) push(e.refundable ? 'contributionsRefundable' : 'contributionsCapital', e);
  }

  for (const m of ledger.movements) {
    if (!vale(m.date)) continue;
    if (m.kind === 'CONTRIBUTION') {
      push(m.refundable ? 'contributionsRefundable' : 'contributionsCapital', m);
      continue;
    }
    // Un retiro se parte: lo que cancela deuda NO es lo mismo que lo que se
    // saca de más, y el dueño pidió verlos separados.
    const aplicado = Math.min(m.amount, m.applied ?? 0);
    push('debtRepayments', { ...m, amount: aplicado });
    push('ownerDraws', { ...m, amount: Math.max(0, m.amount - (m.applied ?? 0)) });
  }

  for (const c of ledger.loanPayments) {
    if (vale(c.date) && c.paidBy === 'BUSINESS') push('loanPayments', c);
  }

  return out;
}
```

> ⚠️ **Un gasto operativo de la contraparte emite DOS asientos** (`expenses` o
> `filament`, **y** `contributionsRefundable`/`Capital`). No es un bug: así
> suma hoy `businessCash`, y es la regla que evita la doble carga —una compra
> que paga la contraparte es gasto **y** aporte a la vez, y se anulan en el
> saldo. Dejarlo en uno solo cambiaría `balance`.

- [ ] 1.4 — Reescribir `businessCash` como un `reduce` sobre `cashEntries`,

```ts
export function businessCash(ledger: CashLedger, until?: Fecha): BusinessCash {
  const acc: Record<CashCategory, number> = {
    collected: 0, expenses: 0, filament: 0, equipment: 0,
    contributionsRefundable: 0, contributionsCapital: 0,
    debtRepayments: 0, ownerDraws: 0, loanPayments: 0,
  };
  for (const e of cashEntries(ledger, until)) acc[e.category] += e.amount;

  const balance = (Object.keys(acc) as CashCategory[])
    .reduce((s, k) => s + CASH_SIGN[k] * acc[k], 0);

  return {
    collected: round2(acc.collected),
    expenses: round2(acc.expenses),
    filament: round2(acc.filament),
    equipment: round2(acc.equipment),
    contributionsRefundable: round2(acc.contributionsRefundable),
    contributionsCapital: round2(acc.contributionsCapital),
    debtRepayments: round2(acc.debtRepayments),
    ownerDraws: round2(acc.ownerDraws),
    loanPayments: round2(acc.loanPayments),
    balance: round2(balance),
  };
}
```

/**
 * El detalle de UNA línea de "De dónde sale el saldo".
 *
 * ⚠️ NO reclasifica: pide los asientos a `cashEntries`, el mismo que usa
 * `businessCash`. Si acá hubiera filtros propios, el detalle sumaría distinto
 * que la línea de arriba el día que uno de los dos cambie.
 */
async breakdown(organizationId: string, category: CashCategory) {
  const d = await this.datos(organizationId);
  const etiquetas = this.etiquetas(d);

  const entries = cashEntries(d.ledger)
    .filter((e) => e.category === category)
    .sort((a, b) => (a.date === b.date ? 0 : a.date < b.date ? 1 : -1)) // más nuevo primero
    .map((e) => ({
      date: e.date,
      amount: e.amount,
      ...(e.id ? etiquetas.get(e.id) ?? { label: 'Sin detalle', source: 'MANUAL' } : { label: 'Sin detalle', source: 'MANUAL' }),
    }));

  return {
    category,
    total: entries.reduce((s, e) => s + e.amount, 0),
    entries,
  };
}
